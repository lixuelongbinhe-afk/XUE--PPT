# 交付与核验

## DOCX 与 PDF
使用用户指定的 Documents/PDF 插件；读取对应技能，先通过 load_workspace_dependencies 定位宿主运行时。保留原模板并在工作副本编辑，遵循竞赛页边距、字体、行距、编号、表格、目录、图题、引文、匿名与文件名要求，用户/竞赛规则覆盖工具默认风格。

两者同时需要时，通常先生成 DOCX，再从同一版源文件导出 PDF，以减少文字差异。若工具失败改用另一个生成器，重新核对二者内容并记录独立生成。只有 PDF 请求时无需把 DOCX 强加为交付物，工作中可有中间文件。

运行宿主要求的 artifact operation marker（若可用且必需），按技能规定使用 bundled runtime；禁止猜测路径或复制托管运行时进入插件包。DOCX 使用 render_docx.py 渲染，PDF 使用 Poppler 等可用工具；必须打开页面图检查，不能只看 XML/抽取文本。

## 五项检查
1. requirements：每个强制要求有对应内容与可执行验收；页数、字数、匿名和附件齐全。
2. evidence：关键数字和论断有来源，引用确实支持结论；标注假设、计划与缺失。
3. consistency：项目名称、版本、指标、预算、图号、引用在所有产物一致。
4. structure：文件可打开，目录/链接/参考文献正常，DOCX/PPTX 内部结构、PDF 页数与字体无异常。
5. visual：所有最终页已实际查看，无溢出、遮挡、缺字、坏表格、分页异常。渲染失败记 unverified，不能通过。

qa.json 记录各项状态、证据和检查时间，覆盖当前输出文件哈希。修复之后重渲受影响页面，更新 QA；若全局样式变化应全量检查。PPTX 检查普通文字/图形可编辑性，图表是否可编辑如实说明，不因文件扩展名是 PPTX 就声称全可编辑。

## 交付报告
用中文说明：请求文件 → 实际路径 → 完成/草稿/未完成；采用路线、自动替代、跳过内容及原因；验证覆盖、未验证项、对强制要求影响；待用户补充的事实与建议下一步。未满足强制项或任一交付物/QA 失败时只能部分完成。

只返回用户请求的成品和简短报告；渲染页图等默认留工作目录供复查。不得自动把成果上传参赛平台、部署公开网页或发给他人。即便所有生成器失败，也返回实际已完成分析和失败摘要；不生成空文件冒充结果。
